\title{\Large \bf Short Paper: Gnomon: A Streaming Storage Engine for Temporal Graphs}

% Double-blind: no author identification.
\author{Anonymous submission}

\maketitle

\begin{abstract}
Temporal graphs whose edges are immutable timestamped events (audit streams, agent execution traces, interaction logs) are
ingested as
never-ending, near-sorted streams; queried along time and causality;
and retained under time-based policies. No deployed storage layer
serves this combination: entity-keyed graph stores demote the
timestamp to a payload attribute, columnar and LSM engines pay a join
per traversal hop, versioned temporal graph stores assume few
property-rich versions per entity, and statically time-sorted layouts
answer queries well while being unable to ingest at all.

\sys keys storage on time itself: each timestamp maps to a virtual
address by a constant-time shift, and demand paging absorbs temporal
sparsity, so no index is built or maintained. Ingestion becomes a
lock-free $O(1)$ append independent of arrival order; retention
becomes a page release over an address prefix; compaction is explicit
and off the ingest path; queries remain correct \emph{during}
concurrent ingestion through a per-slot publication protocol; and
because engine state is a pure function of the edge multiset, recovery
is re-ingestion. We evaluate \sys against a columnar engine, three CSR
layouts, and the most recent versioned temporal graph store, with
element-wise answer verification, on fourteen datasets including a
billion-edge enterprise corpus, and show that keying storage on time
wins the streaming and traversal axes by orders of magnitude while
conceding bounded, measured costs on the structural axis.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A growing class of graphs is built from \emph{events}. A system call
touches a file; an agent invokes a tool; a host authenticates to
another; a user replies to a message. Each edge carries the moment it
happened, never changes afterwards, and arrives as part of a stream
that does not end. For a storage system this combination is unusual
and demanding: writes are append-only and unbounded, reads are
constrained by time and causality rather than by key, and the
retention policy, keeping the last $N$ days, is itself a predicate on
the write key. A single endpoint under ordinary load emits tens of
thousands of such events per second, and a fleet multiplies that, so
what the layout does with the time dimension determines the write
path, the read path, the eviction path, and the recovery path at once.

Existing storage engines all approach this workload with a layout
designed for something else. Dynamic graph
stores~\cite{wheatman2021ppcsr, shen2026dcsr, dhulipala2019aspen,
fuchs2023sortledton, pandey2021terrace, deleo2021teseo, zhu2020livegraph,
kumar2019graphone} key storage on source-vertex identity and treat the
timestamp as payload. A time-constrained query then becomes a
structural scan with a per-edge filter, and a retention pass has to
find expired edges wherever vertex order scattered them. Columnar and
LSM engines~\cite{raasveldt2019duckdb} have the opposite problem:
ordered by time, they answer range filters well, but every hop of a
traversal is a fresh join against the edge table. Versioned temporal
graph databases~\cite{li2026tva, hou2024aeong} solve a different
problem, retrieving the valid \emph{version} of an updated entity, and
their structures assume few, property-rich versions per
entity, which an event stream violates by construction. A statically
time-sorted CSR answers temporal queries close to optimally, but it is
not a storage engine: its only update path is a full rebuild, and
during that rebuild it is blind.

\sys keys storage on time. The starting observation is that a 64-bit
virtual address space is orders of magnitude larger than the time
range of any recorded workload, so instead of maintaining an index
from timestamp to location, we let the timestamp \emph{be} the
location:
\begin{equation}
A(T) \;=\; A_{\mathrm{base}} + \big((T - T_{0}) \gg S\big)\times P,
\label{eq:mapping}
\end{equation}
one subtraction and one shift, with the operating system's demand
paging absorbing temporal sparsity at no data-structure cost.

What follows from that layout is the point of the paper. An edge's
home is computed, not searched, so ingestion is a wait-free slot
claim; the computation ignores arrival order, so late events cost
nothing extra; retention is a monotone predicate on time, so expiry
releases an address prefix; and nothing is updated in place, so
recovery is replaying an append-only log through the normal insert
path. None of these is engineered on top of the layout; each is a
consequence of it.

Time-ordering itself is not new. Log-structured file
systems~\cite{rosenblum1991lfs}, LSM trees~\cite{oneil1996lsm} and
time-series stores~\cite{pelkonen2015gorilla} have organised writes by
time for decades, but in all of them an auxiliary structure still maps
keys to the data: sorted runs and a manifest, or per-series chunk
indexes. \sys removes that level. Because the key \emph{is} the time
and the time \emph{is} the address, there is no run, manifest or chunk
index to maintain, merge or recover, which is why compaction here is
optional rather than structural and recovery is replay rather than log
analysis~\cite{mohan1992aries}.

The design also has costs, and a storage paper owes their measurement
as much as their mitigation. A layout that refuses to organize by
entity must pay something on entity-keyed operations, and one that
never sorts during ingestion must either scan unsorted neighborhoods or
sort them later. We measure both and report the operations where a
competing design beats us outright (\cref{sec:eval}).

We contribute: (i)~a storage design that keys temporal graphs on time,
with proofs for its addressing, space, granularity, and concurrency
properties (\cref{sec:design}); (ii)~a publication protocol under
which readers never observe a torn or unpublished edge during
lock-free multi-writer ingestion (\cref{thm:conc}); and (iii)~an
evaluation against two streaming graph stores, a columnar engine and
three CSR variants that verifies element-wise answer equality before
reporting any latency, and that evaluates recovery rather than merely
asserting it (\cref{sec:eval}).

\subsection{Time-keyed addressing}
\Cref{eq:mapping} maps a timestamp to a slot in one anonymous memory
mapping (\cref{fig:arch}). Two properties turn that arithmetic into a
storage layout.

\begin{theorem}[Addressing]
\label{thm:addr}
For any timestamp $t$, the slot holding every edge stamped $t$ is
computed in $O(1)$ worst case, with no data-dependent memory access.
\end{theorem}
\begin{proof}
The map is one subtraction and one shift. Two timestamps land in the
same slot exactly when $\lfloor (t-T_0)/2^S \rfloor = \lfloor
(t'-T_0)/2^S \rfloor$, i.e.\ when they share a window, so every edge
stamped $t$ is registered under that one index and no other slot can
hold one. No search structure is consulted, so the bound is
unconditional rather than expected-case. A B-tree or LSM index gives
$O(\log E)$ with pointer chases; a hash index gives \emph{expected}
$O(1)$ with worst-case collisions.
\end{proof}

\begin{theorem}[Space]
\label{thm:space}
Let $P$ be the page size and $W_{occ}$ the number of non-empty
windows. Resident timeline memory is at most $W_{occ}\cdot P$ plus
page-table overhead the kernel materializes lazily; untouched windows
cost zero bytes, whatever the virtual reservation.
\end{theorem}
\begin{proof}
The timeline is an anonymous mapping of pointer slots. A page becomes
resident only when first written, and a slot is written only when its
window receives its first edge. Resident pages are therefore at most
the number of pages holding at least one occupied slot, which is at
most $W_{occ}$ since each occupied slot dirties one page. Untouched
ranges are never faulted in and never appear in the page table.
\end{proof}

Sparsity is absorbed by the MMU, not by a structure the engine
maintains. The mapping is \emph{anonymous}, so the failure modes
catalogued against mmap in databases~\cite{crotty2022mmap}, namely torn
file pages, SIGBUS on truncation and eviction stalls, do not apply: we
use
mmap as an allocator reserves address space, not as a buffer pool.

The shift $S$ sets how much time one slot covers. Too coarse and
windows overfill; too fine and the timeline sprawls. \sys picks $S$
from stream statistics, and the choice is bounded.

\begin{algorithm}[t]
\small
\DontPrintSemicolon
\KwIn{event count $E$, span $L$, target occupancy $\tau$}
\KwOut{shift $S$}
$D \leftarrow \max(1, \lfloor E/\tau \rfloor)$ \tcp*{windows we want}
$w \leftarrow \max(1, \lfloor L/D \rfloor)$ \tcp*{width we want}
$S \leftarrow \lceil \log_2 w \rceil$ \tcp*{width we can address}
\Return{$S$}
\caption{Adaptive granularity selection. Runs once on a stream
prefix; re-running on a later prefix changes only future windows,
since \cref{eq:mapping} is evaluated per edge at insert time.}
\label{alg:shift}
\end{algorithm}

\begin{theorem}[Granularity]
\label{thm:shift}
For $E \ge 2\tau$ events with target occupancy $\tau$, the selected
shift yields mean window occupancy $\mu \in [\tau/2,\, 4\tau)$.
\end{theorem}
\begin{proof}
The selector computes $D=\lfloor E/\tau \rfloor$ desired windows, a
desired width $w=\lfloor L/D \rfloor$, and takes the smallest $S$ with
$2^S \ge w$, so $2^S \in [w, 2w)$. The realized window count
$W=\lceil L/2^S \rceil$ then satisfies $D/2 < W \le D+1$, giving
$\mu = E/W \ge E/(D+1) \ge \tau/2$ and $\mu < 2E/D < 4\tau$.
\end{proof}

The two factors of two are real, not slack: one from rounding the
window width up to a power of two, which shift addressing cannot avoid,
one from the ceiling on the window count. Across our corpora a single
target yields per-window densities from 32 to 32{,}768 edges, and the
bound holds at both ends.

\subsection{Lock-free ingestion, correct concurrent reads}
\label{sec:design-ingest}
An insert computes its slot (\cref{thm:addr}), claims an index in the
window's block with one \texttt{fetch\_add}, and installs overflow
blocks by CAS. Every failed CAS means some other insert succeeded, so
ingestion is lock-free and the slot claim itself is wait-free. Nothing
sorts and nothing rebalances, so arrival order does not matter. That is
what separates \sys from every sorted-on-ingest design as soon as
events arrive late or out of order.

Readers are protected by a publication protocol instead of locks. A
writer fills an edge's payload first and stores its timestamp
\emph{last} with release semantics. Fresh arena pages are zero-filled,
so a zero timestamp marks a slot that is not yet published; readers
acquire-load the timestamp and skip those. Vertex-index references
publish through their block pointer the same way. One extra ordering
rule makes the fast read path safe as well: an append clears the
bucket's \emph{sorted} flag \emph{before} it bumps the bucket counter.

\begin{algorithm}[t]
\small
\DontPrintSemicolon
\SetKwProg{Fn}{}{}{}
\Fn{\textsc{Append}$(e)$}{
  $b \leftarrow$ block for slot $(e.t - T_0) \gg S$ \tcp*{\cref{thm:addr}}
  $b.\mathit{sorted} \leftarrow \bot$ \hfill \textsf{(release)}\;
  $i \leftarrow \textsc{FetchAdd}(b.\mathit{count}, 1)$ \hfill \textsf{(acq-rel)}\;
  \lIf{$i \ge b.\mathit{cap}$}{install overflow block by CAS; retry}
  write $e.\mathit{src}, e.\mathit{dst}, e.w$ into $b[i]$\;
  $b[i].t \leftarrow e.t$ \hfill \textsf{(release: publishes the slot)}\;
}
\Fn{\textsc{Expand}$(v, t_{lo}, t_{hi})$}{
  \ForEach{bucket $b$ of $v$}{
    $n \leftarrow b.\mathit{count}$ \hfill \textsf{(acquire)}\;
    \lIf{$b.\mathit{sorted}$ \textsf{(acquire)}}{binary-search $b[0..n)$}
    \lElse{scan $b[0..n)$, skipping $t = 0$}
  }
}
\caption{Publication protocol. The two release stores and the order of
lines 3--4 are what \cref{thm:conc} rests on: clearing \emph{sorted}
before bumping \emph{count} is what lets a reader trust a binary
search, and storing $t$ last is what makes a half-written slot
invisible.}
\label{alg:publish}
\end{algorithm}

\begin{theorem}[Concurrent reads]
\label{thm:conc}
Under this protocol no query observes a torn, partial, or unpublished
edge during concurrent multi-writer ingestion, and a reader that finds
the sorted flag set may binary-search the counted prefix.
\end{theorem}
\begin{proof}
For the first claim: a reader only accepts a slot whose timestamp is
non-zero, and the writer's release store of the timestamp happens
after its payload writes, so an acquiring reader that sees the
timestamp also sees the payload. A slot is written once and never
mutated, so no torn state exists after publication.

For the second: a reader loads the counter (acquire) and then the
flag. Suppose it observes the flag still set. Any append that could
have extended the counted prefix cleared the flag before bumping the
counter, and the reader's acquire on the counter synchronizes with
every bump it observes; so if any such bump were visible, the
corresponding clear would be visible too and the flag would be unset.
The observed prefix is therefore exactly the one compaction verified
and published, and binary search over it is sound.
\end{proof}

\subsection{The compaction contract}
Appends leave a vertex's neighborhood in arrival order, so a
time-windowed expansion has to scan it: $O(d)$. An explicit
\texttt{compact()} pass sorts each neighborhood by timestamp once, and
afterwards expansion binary-searches in $O(\log d + k)$ for $k$
results. Compaction is deliberately \emph{not} on the insert path: an early
build that compacted after every batch ingested at 11K events/s,
because each batch re-walked the whole index, which is the same
$O(\text{index})$-per-batch cost a sorted structure pays by design.

Queries are correct in both states; compaction changes their cost, not
their answers. This is the paper's central trade. A statically sorted
structure gets its query speed by making sorting \emph{mandatory} and
pays with a rebuild window during which its answers are wrong
(\cref{sec:eval-stream}); \sys makes sorting \emph{optional} and pays a
bounded constant until it runs. The contract is: \emph{always
appendable, always correct including mid-ingest; fast expansion after a
compaction you schedule when convenient.}

\subsection{Retention and durability}
Retention is a monotone predicate on time, so under \cref{eq:mapping}
it is an operation on an address prefix. \texttt{evict\_before($t$)}
walks the timeline prefix, merges the block extents it finds, and
returns whole pages to the OS with \texttt{madvise}; readers of other
windows are untouched. There is no scan of the edge set and no
tombstone compaction, because expiry and address order coincide.

\label{sec:design-durability}
Durability uses a property most databases do not have: engine state is
a pure function of the edge multiset. Edges are immutable, never
updated, and deletion is retention policy rather than semantics. The
log is therefore just framed, checksummed batches of raw edges; an
asynchronous writer overlaps it with insertion; and recovery is
replaying the log through the ordinary insert path. There is no undo
phase, no redo phase, and no idempotence bookkeeping, because
replaying a batch twice is indistinguishable from the multiset having
contained it twice, which it cannot, since each batch is framed once. A
torn tail frame fails its length or checksum test and is discarded.

\section{Implementation}
\label{sec:impl}
\sys is $\sim$6,500 lines of dependency-free C++17: the engine, nine
graph algorithms, converters for two audit-log formats, and seven
correctness suites, among them a multi-writer/multi-reader stress test
of \cref{thm:conc}. Interior windows of a range scan are copied without
any timestamp comparison, since only boundary windows can contain
out-of-range edges, and boundary scans are AVX2-vectorized. Source,
converters, and every experiment driver will be released.

\section{Evaluation}
\label{sec:eval}

\textbf{Setup.} 20-core Xeon, 188\,GB RAM, Ubuntu 20.04. Fourteen
corpora spanning five orders of magnitude (\cref{tab:breadth}): LANL
enterprise authentication~\cite{lanl2015data} (1.05B events, 17,666
hosts, 58 days), DARPA TC whole-system provenance (CADETS 22.5M and
THEIA 97.3M information-flow edges), and 12 public temporal
graphs~\cite{leskovec2014snap} from 60K to 113M edges. Baselines, all driven in-process:
GraphOne~\cite{kumar2019graphone} and LiveGraph~\cite{zhu2020livegraph}
built from source; DuckDB v1.5.5 through its C API; a time-sorted CSR
(\texttt{tcsr}, the strongest static competitor), an arrival-order
entity CSR (\texttt{ucsr}), and a topology-only CSR; and
TVA~\cite{li2026tva} via its released artifact. Before any latency is
reported we check that the engines returned the same answer element by
element. Latencies are heavy-tailed, so we report medians with tails or
results binned by answer size, never means.

\subsection{Ingestion}
\label{sec:eval-ingest}
Across the 13 corpora of \cref{tab:breadth}, \sys ingests at
7.0--94.6M~events/s on eight threads, the one optional compaction pass
costing at most 3.8\,s on the largest (113M edges). Rate tracks arrival
density rather than corpus size: the two audit-log corpora, whose events
crowd into days rather than years, are the fastest.

The billion-edge LANL corpus is absorbed at 77.5M~events/s, and the
rate does not decay as history accumulates: streaming 256M of its
events in sixteen equal chunks holds 51.2--56.5M from the first chunk
to the last, memory linear in edges, no event refused.

Readers cost the writer less than durability does. With four issuing
validated windowed queries throughout, ingestion falls from 47.9 to
36.6M~events/s on wiki-talk and 43.5 to 29.7M on stack-overflow, and
across three corpora every query over a window the stream had already
passed returned the answer a quiescent engine gives, on every one of
hundreds of thousands of repetitions. Forcing the log to stable storage
costs far more: the same stream absorbs 57.4M with no log and 28.8M
with a log written but never flushed, which is the contract GraphOne's
log implements, against 6.5M under 64\,MB group commit and 1.1M with an
fsync per batch.

A versioned temporal store is the wrong shape for this load rather than
merely slower: driving TVA's artifact with the same stream did not
finish wiki-talk's 7.8M events in 90 minutes, at 41.6\,GB RSS
(\cref{fig:streaming}a), because every repeated $(src,dst)$ contact
extends one edge's version chain and inverts its assumption of few,
property-rich versions per entity.

\subsection{Time-respecting traversal}
\label{sec:eval-traversal}
On multi-hop time-respecting traversal run to fixpoint, \sys leads
DuckDB by $150$--$700\times$ across all answer sizes; at $|R|>1{,}000$
the median is 12\,ms against 2.43\,s (\cref{fig:temporal}a). The
reason is structural: each hop costs a relational engine a join
against the edge table. The time-sorted CSR stays $2.7\times$ faster
than \sys at high degree, which is the measured price of refusing to
sort during ingestion; \cref{sec:eval-stream} prices what the CSR pays
for that privilege.

Against an \emph{ingesting} entity-keyed layout the ordering flips with
density (\cref{fig:temporal}b): its per-delivered-edge cost rises from
26\,ns at degree 6 to 1{,}500\,ns at degree 59{,}517 because it scans
whole neighborhoods, while \sys's compacted buckets amortise a binary
search and \emph{fall} from 54 to 15\,ns. The crossover sits near
degree 100, inside the range event streams occupy.

Two more results bound the picture. On time-\emph{range} filtering,
DuckDB's home ground, \sys's vectorized scan wins the median
$10.6\times$ (77\,$\mu$s against 819\,$\mu$s) with p95 at parity. And on
structure-only algorithms, decomposing each run into the share spent
delivering adjacency under checksum-verified executions, \sys delivers
at $0.9$--$5.8\times$ the topology-only CSR optimum over 29 measurements
on 11 corpora, median $2.1\times$. The spread separates by access
pattern: frontier-driven traversal stays at $1.4$--$2.2\times$
regardless of corpus size, including on the billion-edge corpus, while
whole-graph iteration walks every bucket chain on every round where a
CSR walks one contiguous array, reaching $5.8\times$ at 69M edges. This
is the concession: the price of not organising by entity, paid for an
ingest path the optimum does not have.

\sys's weakest operation is the full-graph as-of snapshot, answered by
enumerating and reducing: 218\,s on CADETS. That is what TVA's
version-skipping is built for, and we report it as its win.


\subsection{In-category baselines}
\label{sec:eval-baselines}
The comparison a storage reader asks for is against stores built for
the same job. We build two from source and drive all three through one
query list, comparing a checksum over the delivered
$(\mathit{dst}, t)$ pairs so that a faster number cannot be a
different question: 54 of 54 LiveGraph configurations and 9 of 9
GraphOne corpora agree.

Against LiveGraph~\cite{zhu2020livegraph}, ingestion is
$2.7$--$15.7\times$ faster at roughly half the resident set, and
windowed neighbour delivery $1.6$--$194\times$. Against
GraphOne~\cite{kumar2019graphone} the ingest comparison is close,
$0.92$--$2.76\times$ measured like for like against the point its
archiving makes edges visible, and the separation is in the query:
$1.4$--$16.3\times$, because its adjacency carries no order on time
and selecting a window costs it a read amplification of $8$--$84\times$
(4.3B edges scanned to deliver 51M on CADETS). Uncompacted we are
within $1.3$--$1.7\times$ of GraphOne's scan rather than ahead of it;
the separation is what compaction buys.

Run end to end, extracting a window, computing over it with identical
code, and writing results back, extraction on a 63.5M-edge corpus runs
$70\times$ ahead of LiveGraph at a 0.01\% window and exactly level at
100\%: its cost barely moves across a $2000\times$ change in result
size. A columnar engine indexed on time is the closer competitor,
$1.2$--$1.9\times$ behind at narrow windows.

\subsection{Recovery}
\label{sec:eval-recovery}
Recovery is re-ingestion (\cref{sec:design-durability}), which makes it
fast and the claim checkable. Replaying logs from 1M to 1.024B edges
the rate is flat at $16$--$35$M~events/s, and the billion-edge LANL
corpus is back in 29.6\,s. Killing a live writer with \texttt{SIGKILL}
at an arbitrary instant, 50 times over two corpora, the replayed engine
is every time byte-identical to the input prefix and query-equivalent
to an engine built from exactly those edges. A signal cannot produce a
torn frame; truncating the log at a random byte or flipping one bit
inside a frame can, and across 60 such injections replay stopped at the
last intact frame and never admitted a corrupt batch.

\subsection{Rebuild versus stream}
\label{sec:eval-stream}
The time-sorted CSR's only update path is a full rebuild, 28.4\,s on
LANL, and a query served from the pre-rebuild snapshot is not stale but
silently \emph{wrong}: 68 of 100 returned incomplete answers, losing
33.2\% on average and 99.5\% at worst (\cref{fig:streaming}b). \sys has
no blind window. Its own compaction costs about twice that rebuild,
55.7\,s, but the two differ in kind: the rebuild is on the correctness
path, compaction on the performance path. That is the contract.

\subsection{Retention and a real workload}
Under a stream with a retention horizon, memory reaches a steady state
rather than growing: 7.8M events pass through while resident memory
holds at 250--310\,MB, each eviction costing 0.3--0.4\,ms and leaving
the ingest rate undisturbed. Against a columnar \texttt{DELETE},
releasing 90\% of a 16.5M-edge history is $5$--$29\times$ faster; both
reclaim fully, so the win is speed. Tracing all 749 labelled red-team alerts of LANL to
causal fixpoint takes 46.5\,s in total (median 24.6\,$\mu$s, p95
353\,ms), and on DARPA CADETS a forward trace reconstructs the
published attack chain in causal order inside an impact set 0.0093\% of
the graph, at 133\,$\mu$s.

\textbf{Negative results, kept.} Backing the dense arenas with 2\,MB
pages was implemented and measured
and loses: on 240M LANL events it costs 28\% of ingest throughput and
69\% more resident memory, so it ships disabled. Binary search into a
sorted bucket likewise loses below roughly 32 refs. And this original
retention hypothesis, that the columnar engine would mark deleted rows
without reclaiming, was false.

\section{Related Work}
\label{sec:related}
\textbf{Versioned temporal graph stores.} TVA~\cite{li2026tva},
AeonG~\cite{hou2024aeong} and Aion~\cite{theodorakis2024aion} organize
versions of \emph{updated entities} for snapshot retrieval. Delta
encoding and version-chain locality, their central difficulties, do not
arise in an append-only stream, and time-respecting reachability is not
expressible over a snapshot surface. Aion comes closest, indexing
updates by time, but it indexes \emph{revisions} of entities rather
than making time the address of the events themselves.
\textbf{Structural dynamic graph stores}~\cite{wheatman2021ppcsr,
shen2026dcsr, dhulipala2019aspen, fuchs2023sortledton,
pandey2021terrace, deleo2021teseo, zhu2020livegraph} optimize the
entity axis and treat time as payload; none answers time-respecting
queries natively, and \cref{sec:eval-baselines} prices what that costs.
RapidStore~\cite{hao2025rapidstore} also decouples version data from
graph data, but at subgraph granularity, still keyed on vertex id, with
versions reclaimed rather than retained.
GraphOne~\cite{kumar2019graphone} is the closest prior work at this
venue: a dual-format store keeping a recent edge log beside a compacted
adjacency, with a marker bit written after the payload so readers
detect a partial update, the same discipline \cref{thm:conc}
formalises. But its edge log is a staging area that must drain into the
entity-keyed format, and it states it is not designed for arbitrary
historic views; here the time-ordered form \emph{is} the durable form.
LLAMA~\cite{macko2015llama} materialises versions. \textbf{Temporal queries} such as time-respecting reachability are
classical~\cite{wu2014temporalpaths, holme2012temporal}; we adopt their
semantics and supply the layer below the
frameworks~\cite{shun2013ligra, kyrola2012graphchi}.
\textbf{Concurrency.} The append path follows the standard lock-free
discipline~\cite{michael1996nonblocking}; \cref{thm:conc} is a
linearizability argument~\cite{herlihy1990linearizability}.
\textbf{Columnar/LSM engines}~\cite{raasveldt2019duckdb} own predictable
range-filter tails and lose traversal by orders of magnitude; the case
against mmap~\cite{crotty2022mmap} targets file-backed buffer
management, which an anonymous reservation sidesteps.
\textbf{Provenance systems}~\cite{king2003backtracker,
pasquier2017camflow, zhang2025tapas, hassan2020omegalog} motivate the
rates; their reduction techniques~\cite{lee2013loggc} exist because no
storage layer made retention affordable.

\section{Conclusion}
Keying storage on time collapses the machinery an event stream needs:
the index becomes a shift, ingestion an append, retention a page
release, and recovery a replay.
